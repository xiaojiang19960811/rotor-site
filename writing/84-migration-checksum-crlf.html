SQL 一字未改，校验和却变了

结论先说：迁移文件一个字没改，服务启动时迁移器却报 checksum mismatch。问题不在 SQL，也不在数据库，在行尾：历史构建把同一批迁移以 CRLF 嵌进产物，数据库里记的是 CRLF 文本的哈希；如今构建用 LF，SQL 逐行一致，字节却变了，哈希自然对不上。校验和校验的是字节，不是语义。

现象：没人改迁移，启动先报错

一次服务启动，迁移器在第一步就停下：历史迁移的校验和对不上。它认定的事实是"迁移文件被改过"，所以拒绝继续，免得在被篡改的迁移上继续建表。

本地和生产两处同时出现同一报错。这个分布本身就是一条线索：如果只有一处报错，可能是那台数据库的记录出了问题；两处一起报错，说明问题出在迁移文件本身进入两处的方式上，而不是某一台数据库被单独篡改。

校验和只认字节，不认语义

迁移器的校验逻辑很简单：取迁移文件的原始文本算哈希，与数据库里记录的哈希比对。哈希函数不理解 SQL，只看字节。CRLF 是两个字节，LF 是一个字节，同一份 SQL 换个行尾就是另一串字节，哈希必然不同。

所以"内容没变"和"校验和变了"可以同时为真：前者是语义判断，后者是字节判断。把两者混为一谈，就会得出两个错误结论：要么说数据库被篡改了，要么说迁移器坏了。两个都不对，错的是"文件还是原来那个文件"这个假设。

迁移器这么设计是有理由的：它的职责就是发现"迁移文件与当初执行时不一样"。它没有能力、也不应该判断"不一样的是不是语义"。一旦它开始理解语义、放过"看起来没变"的差异，防篡改这道锁就形同虚设。

三条证据，排除"有人改了迁移"

根因锁定之前，先排除最严重的可能性：有人改了已执行的迁移。

  1. 旧产物可复现：从历史构建产物里能提取出当时的 CRLF 文本，重新算哈希，与数据库里的记录完全一致。数据库记的哈希没错，错的是"现在的文件和当时一样"这个前提。
  2. 版本历史无语义变化：翻遍提交历史，迁移 SQL 的语义没有任何改动。唯一的变化是行尾。
  3. 只转行尾即逐行一致：把当前文件只做行尾转换，不动任何 SQL，内容逐行一致。

三条合起来，根因只剩一个：跨平台行尾。历史构建在 Windows 环境下把 CRLF 原样嵌进产物，当前构建在 Git 工作树里用 LF。同一份迁移，在不同环节是不同字节。

修复要克制：窄兼容，不拆锁

修复给这批历史迁移逐一加了 LF/CRLF 哈希窄兼容：每个文件、每个哈希单独列入白名单，迁移器认这两个哈希都是合法的。

克制体现在四个"不"：

  1. 不全局归一化所有历史迁移：只动出问题的那一批，不碰没出问题的。归一化全部历史文件，等于一次性改写所有已执行迁移的字节，风险面比原问题大得多。
  2. 不删除迁移记录：记录是审计链，删了等于销毁"谁、何时、跑过什么"的证据。删记录修校验，是拿审计能力换启动成功。
  3. 不重跑历史迁移：重跑会动业务数据，收益只是一个干净的校验结果，代价不可控。
  4. 不放宽校验：不把 checksum 检查关掉或调松。这次报错恰恰证明锁在正常工作：文件字节变了，它就报警。修行尾问题而拆掉锁，是拿长期安全换短期省事。

验证也按规矩来：完整备份核对无误后启动成功，后续迁移正常应用；另一套生产环境用同一兼容校验也通过。

白名单不是无条件信任

兼容旧哈希之前，必须先验证 SQL 仅行尾不同：逐行比对，确认除行尾外没有任何差异，再把哈希写进白名单，并配回归测试守住它。

顺序不能反：先验证，再兼容。否则白名单就从"已知差异的精确登记"变成"来路不明哈希的放行通道"，下次真有人改了迁移内容，也会被白名单放过去。窄兼容的"窄"，窄在两点：只认这两个哈希，只认这批文件。

复发防护：行尾是发布物的一部分

  1. 迁移文件固定 LF：行尾写进规范，新迁移只用一种行尾，从源头断掉跨平台差异。
  2. 构建环境不得静默改写已发布迁移的行尾：构建只负责打包，不改已发布文件的字节。构建产物里的迁移文件，与仓库里的必须是同一串字节。
  3. 校验报错先查字节，再查内容：看到 checksum mismatch，第一反应应该是"文件字节哪里变了"，而不是"谁改了我的 SQL"。先比字节，再谈语义。

小结

校验和报错时，报错本身不是故障，是防护在生效；真正的故障是字节在无人注意的地方变了。修它要窄、要慢、要留证据；防它要把行尾当成发布物的一部分管起来。
