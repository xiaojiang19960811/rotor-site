Agent 与数字人知识花园

接管一个槽位，就是接管它的全部代价

结论先说：插件系统里，接管一个界面槽位不是"换张皮"，而是"接手一个岗位"。被遮蔽的内置组件不再渲染，它带来的能力也一起消失：分组、归档、改名、新建入口全都不见了。接管方如果只画了自己的新界面、没补上这些旧能力，用户丢的不是一个组件，而是一整条操作路径。接管之前，先列出被接管者原来提供的全部能力，再决定哪些自己补、哪些明确放弃。

槽位有三种，接管只发生在单格槽

客户端用槽位组装页面，插件只能往已经声明的槽里注册。注册必须等声明出现，声明折叠时移除，重声明后重新注册，直接往未声明的槽里注册会在加载时报错。

三种槽的语义不同：

  1. 单格槽：一个位置只渲染一个组件，按优先级排序，排在最前面的胜出。想遮蔽内置组件，就用一个更靠前的优先级压过它的默认优先级。
  2. 列表槽：按顺序叠加多个组件，各自占一块位置。
  3. 键控槽：同样是叠加，但按键名区分，适合一组可独立开关的条目。

声明别人的槽同样报错，组件拿到的属性由框架派生，业务组件不直接接触框架上下文。规则很严，但严是对的：槽位是插件与宿主之间的契约，契约越明确，接管的边界越清晰。

被遮蔽的能力，不会自己回来

一次真实的接管发生在侧栏工作区：数字人 Agent 用自己的工作区视图遮蔽了内置的工作区浏览器。内置组件一消失，它带来的能力也一起消失了：工作区分组、归档、固定、改名、新建工作区入口都不再出现。接管方若要有序退场，得自己列出"其他会话"这类兜底入口，否则用户一旦离开接管视图，就无路可回。

接管还要遵守两条边界：

  1. 打开会话要走服务，不要走属性：标准钩子能读到会话列表和运行状态，但打开会话要走界面服务。服务缺失时应当降级为"只列不可跳"，而不是点了没反应。
  2. 窄栏要自己画：折叠成窄栏时，外壳只告诉你"现在是窄的"，画成什么样是接管方的事；展开侧栏的能力由外壳提供，不能自己改布局。

判断一次接管合不合格，只看一点：接管前后，用户能完成的事是多了还是少了。少了，就是接管方欠账。

安装时机比安装本身重要

接管方踩过的两个坑，都和"什么时候装"有关。

共享样式表必须在依赖它的视图注册和挂载之前安装，通常在插件激活时准备好。只放在面板组件里装，样式就晚了：先渲染的侧栏会拿到一排没有样式的裸按钮，因为组件渲染早于面板首次挂载。模式选择后才启用的可选视图，也要先装样式再注册。

多个组件共读的调色板，不要各自去读持久化存储：持久化写入发生在副作用里，晚于同一轮渲染，先读会拿到旧值。正确做法是用一个模块级的当前主题变量，让所有组件读同一份。

这两条说的是同一件事：插件的安装顺序本身就是功能的一部分，装得晚，等于没装对。

生效方式不同，验证方式也要不同

客户端包的地址带内容哈希，重新打包并安装客户端脚本后，刷新页面即加载新版本，不需要重启应用；宿主插件的改动则必须完全退出并重开。两种生效方式混在一起时，"刷新一下就行"和"必须重启"要分清楚，否则会在"为什么没生效"上反复折腾。

还有两个配套做法值得学：

  1. 开关重开可以重读数据：想让宿主重新读入插件自己的数据文件而不重启应用，可以在插件页把该插件关掉再打开。重新激活会重跑插件的激活逻辑，从而重新读数据。一次真实排障里，这个办法把主管会话从空会话指回了有历史的旧会话，旧记录随之恢复。
  2. 回执要区分"没加载"和"加载后报错"：插件可以经自己的 HTTP 路由写回执，带上构建标识，用它在宿主侧确认"页面到底跑哪一版"。这比浏览器控制台可靠，也便于区分"代码没生效"和"代码报错"。回执要留在加载器之外：加载器抛错时页面仍能写回执，否则最需要证据的时候恰恰没有证据。

单文件入口，拆分要靠构建

宿主只服务一个文件入口，页面靠模块加载器注册；想拆源码就必须有构建步骤，不能指望浏览器原生加载多个模块文件。参考做法是源码按关注点分目录，用打包工具打成一个自执行包，共享库设为外部依赖，不要打进第二份。

构建顺序也有讲究：构建必须排在打包与发行准备之前，包的白名单必须包含入口指向的单文件产物及运行资源，源码目录不进包。忘记构建，可能发出旧产物或缺少入口。

测试同样要跟着产物走：不要按源码文本锚点截取产物，拆模块后锚点与缩进都会失效。正确做法是加载产物加显式测试入口，纯函数直接导入源模块验证。

接管一个槽位，就是接管它原来的全部责任、安装顺序与验证方式。只接管渲染、不接管责任的插件，迟早会把账单寄给用户。
