pip install 成功了，不等于能推理

一次 CPU 容器里装 OCR 依赖的排障，最终锁定的是五个版本号，而不是一个。因为在这个过程里我们发现：安装成功、导入成功、pip check 通过、mock 通过、真实推理成功，是五个互相不能替代的结论。 你在哪一层停下来，就把哪一层的假阴性留给了生产。

故障链条：三个不兼容，一层层往下掉

起点是一个需要在 CPU 容器里跑 OCR 的项目，目标版本是 PaddleOCR 3.0.3。

  • 第一层：自动解析的次生依赖不兼容。只指定了 PaddleOCR，安装器自动抓来 PaddleX 3.7.2，结果它和 PaddleOCR 的 PaddlePredictorOption 构造参数对不上。显式锁定 PaddleX 3.0.3 之后，这层消失。
  • 第二层：旧依赖的旧依赖拖走了解析器。PaddleX 3.0.3 依赖旧版 LangChain 的 docstore 命名空间，安装器转头又自动抓来 LangChain 1.x，import 直接失败。只能把 LangChain 也固定在 0.3 系列。
  • 第三层：未声明的隐性依赖。前两层修好后，Paddle 导入时才发现它依赖 setuptools，而这依赖根本没在包元数据里声明。补上 setuptools 75.8.0，清除掉残留的 LangGraph 1.x（新依赖遗留的不用包），pip check 才真正通过。

最终组合：PaddlePaddle 3.0.0、PaddleOCR 3.0.3、PaddleX 3.0.3、LangChain 0.3 系列、setuptools 75.8.0。这份组合只对这个项目的这一版本有效，不是所有 Paddle 版本的通用建议。

为什么自动解析总坑人

回头看三层故障，有一个共同的根：只锁定了自己关心的包，把次生依赖的解析权留给了安装器。 每次 pip install 的解析结果都是一次独立的决策——当时的仓库状态、当时的其他包、当时解析器的启发式规则，都会改变它。你以为你在重现一个环境，实际上你每次都在重新掷骰子。

这个经验的泛化版本是：锁定的粒度要覆盖到"谁有权做决定"。 如果某个包的行为依赖于它的依赖版本，那么它的依赖版本也是你的配置，不是安装器的配置。PaddleX 依赖 LangChain 的命名空间，这意味着 LangChain 的大版本是这个项目的事实配置，不管它在你的 requirements 里有没有出现。没写出来的配置，就不是配置。

这个角度也解释了为什么"上次能装这次不能"这种问题总是查起来很贵：两次安装的解析输入根本不在同一个版本空间里，你比较的是两个不同的实验，却期待相同的结论。真正可重复的构建，只认锁定的版本清单，不认"上次装成功了"这个历史事件。

五个证据，不能互相替代

这次复盘最有价值的结论不在版本号，而在证据分层：

证据能说明不能说明
pip install 成功安装器按当次解析结果装完了包解析结果在下一次安装时相同；依赖互相兼容
import 成功模块名空间能加载构造参数、运行时行为、端到端链路
pip check 通过声明依赖的版本区间互相满足未声明的隐性依赖；真实推理
mock / 健康接口通过模拟条件下的前端行为模型加载、真实数据、CPU 推理路径
真实推理成功指定版本在指定环境、指定样本下跑通字段准确率、业务事实正确、长期不退化

事后验证我们走了两层真实推理：CPU 上识别合成图片的负数（确认推理链路不是在瞎跑），再对 66 页实际扫描件做 OCR。后者只证明了解析链可运行，字段准确率和业务事实正确是另一个问题，需要另一套评测来证明——一次真实推理的通过，也不能自动升级成"识别正确"。

闭环规则：怎么防止复发

这次的复发检查清单只针对"升级相关依赖"这一个动作：

  1. 在独立镜像里验证，不污染生产镜像；四件事按顺序走：import、pip check、模型加载、真实图片推理，缺一层都不能说验证完成。
  2. 真实图片不能省：mock 测试跑的是接口形状，模型权重、CPU 算子、图像定位都在真实推理里。验证时保留负数、关键字段和图像定位的检查项，这些才是推理链路真实跑过的痕迹。
  3. 模型缓存独立持久化：别让每次构建重新拉模型，也别让缓存污染结论。
  4. 新版本不直接全量升级：当前组合能不能被新版本替换，仍待一次完整的独立验证；版本号涨了，证据不涨——没证据的升级就是赌。

一句话收束：依赖问题从不在你停下的那一层暴露，它永远躲在你没验证的那一层。
