协议帧写出去了，不等于输出开始了

结论先说：上游说"服务器过载，请稍后再试"，这不是一次普通失败，而是一次应该换号重试的瞬时错误。网关当时把它按普通失败直接返回了，原因有三层：瞬时错误的识别规则没认全这句文案；失败事件的处理顺序让通用规则抢在了故障转移前面；流式响应里先到的空结构事件被当成了有效输出，提前堵死了换号的路。修完之后，切号的判断标准变了：不再看"写没写过协议帧"，而看"写没写出真实语义输出"。

现象：一句报错，走了错路

用户反馈里，上游那句"Our servers are currently overloaded. Please try again later."还在以普通失败的形式返回。受影响的入口有三处：普通 HTTP 请求、Chat 与 Responses 兼容层、以及流式响应里的失败事件故障转移。同一句报错，在 WebSocket 路径的映射里已经被覆盖，说明漏点不在状态码映射，而在 HTTP 与流式共用的瞬时判定：规则是按入口各写一份的，漏一处就漏一条路。

三层根因

  1. 识别规则没认全：瞬时判定覆盖了处理中、容量不足、服务器过载、降速这几类文案，却没显式包含"Our servers are currently overloaded"这句原话。规则按枚举维护，厂商换一句说法，就多一个漏网的。
  2. 处理顺序排错了：流式响应里上游以失败事件报告过载时，通用透传规则可能先于故障转移规则提交失败事件。错误分类对了也不够，顺序错了，正确的分支根本轮不到。
  3. 空结构事件提前占了位置：流式路径里，上游会先发 output_item.added、content_part.added 这类空结构事件：它们不含真实 token，只是协议壳子。但网关把它们当作客户端的有效输出写了出去。等到真正的过载失败事件到达时，响应"已经开始了"，换号的窗口已经关闭。

第三层最值得展开：网关原来用"是否已经向客户端写过东西"判断能不能切号。协议帧也是"东西"，于是几个空壳事件就把路堵死了。

修复：四处改动，一个新标尺

  1. 瞬时判定补上两个匹配：完整的过载文案，以及"请稍后再试"加"过载"的组合。
  2. 失败分支调换顺序：过载、容量不足、限流先进入故障转移，再考虑通用透传。
  3. 空结构事件延迟提交：只有携带真实内容时，才算第一个有效输出。
  4. 切号判断改看新标记：是否已写出真实语义输出。协议壳子、SSE 心跳、空结构帧都不阻止切号；文本增量、工具参数、图片结果这些真实输出写出后，才停止切号。

前三处是补漏，第四处是换标尺：继续维护"哪些结构事件算输出"的黑名单只会越列越长，不如直接问一句：真东西写出去了吗。

还有两条防复发措施值得记：长期策略是优先判断真实语义输出是否开始，而不是继续枚举所有协议结构事件；WebSocket 路径保留独立的状态码解析，不把一句文案只修到一个入口：同一错误，修一处不等于修全了。

验证与边界

回归测试覆盖了三点：过载文案能被识别、失败事件优先走故障转移、空结构事件之后再来过载仍然可以切号。修复随一次蓝绿发布上线，发布后 90 秒观察窗口里，那句过载报错、转发失败标记与崩溃类日志都没有再出现。

两个边界要说清楚。第一，第一次发布本身就出了岔子：手工构建漏了一个嵌入前端的参数，首页直接返回 404，靠同版本二次蓝绿发布才修复。修故障转移的版本，自己发布时也要先过一遍发布流程。第二，发布后上游真实的过载响应仍在出现：修的是"认不认得出来"，不是"让上游不再过载"。上游容量问题还会发生，但现在它会走进瞬时处理路径，而不是被当成普通失败直接返回。

还有一个未解的收尾：如果真实输出已经写出去了，之后再来过载，流内只能以失败事件合规终止，无法无缝换号。这是切号机制的硬边界，不是下一个补丁能解决的。

一句话收束：判断能不能切号，别数写过几个协议帧，问一句真东西写出去了没有：没写出，就可以换；写出了，就只能认。
