# 模型只管提计划：Agent 副作用的三道门

> 栏目：知识花园 ｜ 合集：Agent 与数字人 ｜ 来源：wiki/concepts/Agent执行编排与外部副作用边界 ｜ 状态：初稿

**结论先行：** Agent 出事故，几乎都发生在"计划"和"执行"之间。模型提了计划，系统却把它当成了执行许可。真正能用的边界是：计划生成、路径补全、节点执行、外部写入是四个可区分的阶段。模型只能做第一件事；凡是有副作用的动作，必须过三道门：明确声明、授权校验、可恢复的持久化状态。

## 四个阶段，各做各的事

一个能自主做事的 Agent，内部至少要拆成四段：

1. **模型计划**：解析用户意图，提出候选的能力节点和目标，不直接执行任何外部动作。
2. **路径补全**：编排器按能力契约，把计划里缺失的中间环节补齐，只允许补无副作用的中间节点。
3. **节点执行**：按依赖就绪、资源锁、暂停/恢复/取消的规则跑 DAG，每个节点结果可追溯。
4. **副作用写入**：通知、创作、发布、外部系统调用，由独立的 handler 承担，在真实结果确认后才推进后续节点。

为什么必须分阶段？因为每一阶段的"证据"不一样：计划是对的，不代表路径是全的；路径是全的，不代表执行是成功的；节点显示执行成功，不代表用户真的收到了结果。阶段不分开，出事时连哪一环坏了都定位不了。

## 计划不是许可

最危险的一个误解：模型在计划里写了"发送飞书通知"，系统就当作已经拿到了发送许可。

正式边界有三条：

- 模型计划里的外部动作只是提议。通知、创作、发布、写入、删除，必须由模型计划明确声明，再走授权与状态门禁。
- 能力路径自动补全只能补确定、无副作用、有输入输出契约的中间节点，不能凭空增加通知、创作或发布节点。
- 不能用自然语言正则或固定节点名绕过能力注册表和授权校验。计划里写了什么不重要，重要的是注册表里有没有这个能力、用户有没有授权。

换句话说：模型的话语权止于提议，执行权在编排器手里。这是对模型最基本的"不信任"，也是整个 Agent 系统里最便宜的一道保险。

## 副作用的三道门

凡是会留下外部痕迹的动作——发通知、做创作、发内容、写数据、删数据——必须过三道门：

**第一道：声明。** 副作用必须在模型计划里明确声明，没有声明就没有执行。模糊的意图（比如"顺便做点创作"）必须在指令识别阶段就被归类到明确的创作节点上，不能靠事后审查去猜。

**第二道：授权。** 声明之后逐项校验：能力注册表里有没有这个能力、用户授没授权、节点的输入输出和依赖关系对不对。未知能力不能降级成近似任务凑合执行；审查轮对结构错误做有限次修复，修不好就失败，不要硬跑。

**第三道：恢复。** 这是最容易被忽略的一道。暂停、恢复、取消、重试和进程重启，必须基于持久化的执行状态，避免重复副作用。异步外部任务在真实完成或明确失败之前，不能把工作流提前标记为成功，也不能伪造最终链接或投递结果。

第三道门有一个推论：凡是不能幂等的副作用，执行前就要想好失败了怎么收场。重试三次发三条通知，比不重试更糟。

## 真实案例一：飞书只发了首个结果

来源：知识库 bug 记录，2026-08-27，数字人 Agent 项目。

用户来信要求同时查看两位歌手的近况并发送飞书。两个研究节点都完成了，飞书交付状态显示已发送，但实际消息里只有第一位歌手的结果。

根因在执行端：飞书 handler 会等待所有依赖节点完成，但组装摘要和来源时只读取了第一个依赖。节点状态全是完成，发送状态是成功——每一盏灯都是绿的，但用户收到的内容是残缺的。

这就是"只看状态"的代价：测试只断言了发送状态，没断言用户可见正文和来源集合。修复后立下的防复发规则是：多输入交付节点的回归测试，必须同时断言依赖等待、用户可见正文、来源集合三个层次，不能只看发送状态。

## 真实案例二：模糊的创作意图被漏掉了

来源：知识库 bug 记录，2026-09-17，数字人 Agent 项目。

测试来信说："帮我找找信息，并且发飞书给我，哦对了，再想办法做点创作。"研究和飞书通知都完成了，但创作步骤根本没生成。

已确认的原因：指令解析规则里没有明确规定"做点创作"属于创作指令，审查轮于是接受了一个只有研究与通知的计划。关键词兜底只负责图片输出这类参数，不能替代意图识别。

修复是在指令识别与审查规则里明确：未指定媒介的"做点创作"类表达，必须保留创作意图，落到明确的创作节点上，并补了回归测试。

两个案例正好对应三道门里的第一道和第三道：一个是声明阶段漏了意图，一个是确认阶段只看了状态没看结果。

## 测试也要按阶段分开验证

执行编排的测试，不能只验证 Planner 的输出。至少要分别覆盖：能力路径、授权拒绝、依赖失败、资源锁竞争、节点恢复、外部 handler 的真实状态、重复提交、最终用户可见结果。

Mock 可以验证界面与编排形状，但不能替代真实外部系统的端到端验证。这一点和发布证据链互补：那一篇讲哪些验证结果能支持什么发布结论，这一篇讲什么可以执行、何时产生副作用。

## 小结

模型负责提计划，编排器负责守边界。计划、补路、执行、副作用，四件事四个阶段；副作用过三道门：声明、授权、恢复。以后看到一个 Agent，第一件事就问：它的副作用走哪几道门？答不上来，自主程度就要打个问号。
