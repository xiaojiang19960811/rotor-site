# 只改了 3 封，任务就被标成已完成

> 栏目：实验日志 ｜ 合集：Agent 与数字人 ｜ 来源：wiki/bugs/数字人 Agent 世界来信口吻修复假完成（已脱敏） ｜ 状态：已写稿·即将发布

结论先说：数字人 Agent 上一个一次性批量任务，要把一批世界来信的口吻统一修一遍，只改了 3 封，任务记录就被标成已完成，结果还是空的。更糟的是，标成已完成之后，任务再也不会重新入队：回信重写和关系记忆重抽这两件后续工作，也就一直没开始。失败会重试，假完成不会：一次错误的"完成"，比一次失败贵得多，因为失败走的是重试的路，假完成走的是"不用再管"的路。

## 三处记录，三个说法

出事之后，三处记录各说各话，没有一处能单独讲清真相：

- 任务记录表里，这次批量修复是已完成，结果字段是空。
- 业务状态表里，修复仍是进行中，只记录了 3 封。
- 任务队列里，这次任务先是停滞，随后第二次处理只用了 3 毫秒就"成功"结束，返回值也是空。

3 毫秒改不完一封信，更改不完一批。第二次处理根本没有干活：它只是把一个空结果交了上去，而队列把它当成了成功。判断任务做没做完，不能只看队列的脸色：队列只知道投递成没成功，不知道活干没干完。真正说了算的，是业务状态：修了几封、还剩几封，只有它知道。

## 假完成是怎么发生的

链条一共四环，每环单独看都合理，串起来就是一次假完成：

1. **锁被改短了**：续锁时把 10 分钟的锁改成了 2 分钟。单封改写超过 2 分钟，锁就丢了。
2. **重复投递回放了空结果**：锁丢之后任务被重复投递，投递逻辑看到业务状态还是进行中，就把已有的结果直接返回，而那个结果是空的。
3. **队列把空结果当成功**：队列收到返回值，没有区分"干完了"和"交了个空结果"，直接标成已完成。
4. **幂等键堵死了重试**：任务已是已完成状态，后续发布不再入队。3 封之后的工作，永远排不上队了。

注意这不是发布中断：发布中断会把任务打回排队，并写明"工作进程在完成前重启"。中断走的是重试的路，有记录、有下文；假完成走的是"已完成"的路，没有下文。两种失败看起来都是"任务停了"，代价完全不同：一种还能续上，一种直接丢了后半段。

## 修复：完成要由业务状态说了算

修复分四处，各堵一环：

1. **续锁与锁期一致**：续锁改回 10 分钟，与锁本身的时长相同，不再中途丢锁。
2. **重复投递只回放已完成的结果**：状态还是进行中的，不再当成功回放。
3. **空完成不再抄进任务记录**：队列里出现的空完成，不再写入任务记录表，改成重新入队。
4. **业务未完成时允许重新入队**：口吻修复在业务状态未完成时，可以把已完成的标记重启，再入队接着做。

四处修复共用一个原则：任务完没完完，由业务状态说了算。队列的"已完成"只是投递状态，任务记录的"已完成"只是记录状态，两者都不能代替"活干完了"本身。

## 做法：防假完成的三条规矩

1. **完成必须带证据**：标记完成时，结果不能为空；空结果只能算未完成，不能算完成。
2. **重复投递先问状态**：回放结果之前，先确认业务状态是不是已完成；还在跑的，一律不回放。
3. **幂等键防重复，不防续做**：幂等键拦的是重复执行，不是拦"没干完接着干"；业务未完成时，必须留一条重新入队的路。

## 一句话收束

失败会重试，假完成不会：标"已完成"之前，先问业务状态干完了没有，队列的成功、记录的完成，都不能代替活本身干完。
