# 恢复一个会话，要恢复它的全部状态

> 栏目：知识花园 ｜ 合集：Agent ｜ 来源：wiki/projects/数字人 Agent 客户端主会话归档恢复复盘 ｜ 状态：已写稿·即将发布

结论先说：恢复一个对象，恢复的单位是它的全部状态，而不只是把它弄活。只恢复执行体、不恢复状态标记，用户视角里等于没恢复；判断该不该恢复之前，先把事件分清楚类，否则恢复逻辑自己就会制造新的错乱。

## 一个被"恢复"了却看不见的主会话

一款桌面 Agent 客户端里，团队模式有一个主会话：用户平时对话的主入口。一次升级后，恢复逻辑跑完了，Agent 成员也回来了，但用户还是找不到这个主会话。

排查发现了两个已复现的缺口：

1. **已有主会话被归档后，恢复只恢复了 Agent，而不取消归档。** 成员回来了，会话还躺在归档里，用户在正常列表里看不见它。
2. **问候恢复把系统上下文误当成了用户发言。** 运行时上下文、技能目录、时间上下文这类系统产生的事件，被当成了用户说过话的证据。结果用户看到的"问候"标题来自另一条普通会话，而原主会话的标题根本没变。

两个缺口指向同一个根因：恢复逻辑只盯着"东西在不在"，没盯着"状态对不对"。

## 恢复的单位是状态，不是实体

一个会话不只是一个能对话的实体，它是一组状态：原有标识、名称、历史记录、可见性标记。恢复时漏掉任何一项，用户看到的都是一个残缺的对象。

这次复盘定下的恢复清单是：

1. **保留原标识、原名称和原历史**：恢复不是新建一个长得像的会话，而是把原来的那个拿回来。
2. **可见性标记也是状态**：归档标记必须随恢复一并取消，否则恢复动作在用户视角里没有发生。
3. **顺序有讲究**：先取消归档，再打开。顺序反过来，打开的动作可能落在仍被归档的会话上，等于白做。

更一般地说，凡是"恢复"类功能，验收标准都应该是恢复前后的状态对照表，而不是"功能跑通了"。跑通只证明代码执行了，对照表才证明状态回来了。

## 事件分类先于恢复判断

第二个缺口更值得单独讲：恢复逻辑要回答"用户有没有说过话"、"该不该补一句问候"，前提是先把事件分对类。

会话里不只有用户发言，还有大量系统产生的事件：运行时上下文、技能目录、时间上下文。这些事件出现在同一条事件流里，但它们不是用户行为。把系统事件算成用户发言，恢复逻辑就会得出错误的结论：以为用户已经开过口，于是跳过本该补的问候，或者把问候挂到错误的会话标题上。

修复的原则很简单：**问候判断忽略系统上下文，同时不重复打断真实用户对话。** 也就是说，分类先行，判断在后；系统事件不参与"用户是否发言"的计数。

这里还有一条检查纪律：排查这类问题时，检查本身只读取相关元数据与事件分类，不改写用户日志。诊断工具一旦顺手写了数据，排查就制造了新的现场。

## 恢复的触发点要收敛，不能批量

恢复修好之后，下一个问题是：在什么时刻恢复、恢复多大范围？

这次的收敛方式是：只在两个明确时刻恢复主会话，一是团队运行时首次初始化，二是用户明确点击主成员入口。普通成员与普通会话不批量取消归档。

批量恢复看似省事，实则越界：用户主动归档的会话，系统没有理由替他翻出来。恢复不能比用户意图走得更远。触发点越明确，恢复行为越可预期；可预期，是恢复功能最重要的一条性质。

## 界面隐藏不等于全面禁止

同一批改动里还有一个表述纪律，值得单独记下来。

团队模式收口后，专用会话头不提供普通的归档与改名操作，普通新建和工作区选择入口也被隐藏，打开普通会话会切回原始模式，模式切换不创建额外会话。但与此同时，原生模式、系统菜单、快捷键和接口并没有加后端禁令。

所以正确的表述是"界面上收口了"，而不是"系统全面禁止了"。把界面隐藏写成全面禁止，是用 UI 的状态去承诺后端没有实现的事。用户一旦从另一条路走通，就会认为系统在撒谎——而实际上只是文案越界了。

这个纪律可以推广：任何"某能力被关掉"的说法，都要先问一句，关掉的是入口、是权限、还是后端能力。三者不是一回事，文案只能承诺已经实现的那一层。

## 一句话收束

恢复功能验收时，对着状态清单逐项核对：标识、名称、历史、可见性标记一项都不能少；事件先分类再判断；触发点收敛到用户明确的动作；文案只承诺已经实现的那一层。
