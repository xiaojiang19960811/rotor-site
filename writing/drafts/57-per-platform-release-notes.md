# 一份发布说明，两个平台：顶层字段必然串台

> 栏目：实验日志 ｜ 合集：AI 基础设施 ｜ 来源：wiki/projects/双平台客户端发布说明拆分复盘（已脱敏） ｜ 状态：已写稿·即将发布

结论先说：发布说明不是“这次发布”的属性，而是“某个平台某个版本”的属性。两个平台各自独立发版，却共用清单顶层的一条说明，串台不是偶然，是数据模型写错了粒度。说明必须下沉到平台条目里，缺说明就让发布失败，而不是拿一句模板顶上。

## 新版旁边，贴着另一平台的说明

一款双平台桌面客户端，Windows 与 macOS 各自独立发版。一次 Windows 发版时没有单独带上本平台的说明，发布工具只把一句模板写进了其中一份清单的顶层说明；而下载页读的是另一份清单，那里的顶层说明还留着上一位 macOS 发布者的文字。

结果用户在下载页看到的是：Windows 的新版旁边，贴着 macOS 的说明。版本号是对的，说明是错的。没有人改错页面，没有人贴错链接，页面只是老实地把顶层那条说明读了出来。

这不是页面 bug。页面没有判断“这条说明属于哪个平台”，因为数据里根本没有这个信息：顶层只有一个写位，两个平台只能轮流往同一个格子里写。

## 为什么顶层字段必然串台

两个平台独立发版，意味着三件事各自不同：发版时间不同，版本号不同，说明内容不同。顶层字段却只有一个：它一次只能代表一个平台。

于是错配有两种写法，都会发生：

1. **后写覆盖先写**：一处更新了，另一处没更新，旧说明继续挂在新版本旁边。
2. **两份清单各写各的**：发布清单与下载清单的顶层说明不是同一份数据，一处写了模板，另一处还留着旧文字，读的那一处恰好是旧的。

无论哪一种，用户看到的现象都一样：版本与说明分属两个平台。排查时如果只查页面、只查链接，永远查不到根因，因为页面和链接都没有错。根因在数据模型：说明的归属粒度，比发版的粒度粗了一级。

## 修复：说明下沉到平台条目

修复不是“下次记得带说明”，而是把“记得”变成“不带就发不出去”：

1. **说明跟着平台走**：每份清单里，说明写在各自平台的条目里，历史版本的说明也写在该版本对应平台的条目里；顶层只留一句摘要，不再承担“本版说明”的角色。
2. **缺说明直接失败**：发布时缺任一平台的说明，发布流程直接失败，不写模板句兜底。模板句的问题不是写得不好，而是它把“没写”伪装成了“写了”，让一次缺失在清单里看起来像一次完成。
3. **切换时校验另一平台不变**：切换清单时，除了本平台的改动，还要逐字段核对另一平台的条目：除说明外全部不变。只验本平台通过，验不出串台。
4. **补录复用已发布产物**：事后补说明时，复用已经发布出去的产物，不重新打包，不覆盖首次发布的备份。修说明不应该顺带换掉用户正在下载的东西。

下载页也跟着重排：去掉顶部那条“当前版本”总览，改为两个平台各一张卡片，每张卡片各自显示版本、大小、时间、校验信息与可折叠的本版说明；历史版本按平台展开，各自带各自的说明与下载行。页面结构与数据结构对齐之后，串台就没有地方可藏了。

## 历史说明：宁缺，不编

补录历史说明时还有一条纪律：按“这条说明是否点名该平台、且点名该版本”判定归属。命中了就复用原文，没命中的不补写、不推测、不把别平台的说明挪过来。

对从未单独留下说明的版本，补录时直接写明“该版本未单独保存发布说明”。这句话不好看，但它是真的；一句编出来的说明好看，却会让后来的人把编造当成发布记录。发布记录的第一条纪律，是区分“写过”和“没写过”。

## 一句话收束

说明的粒度必须跟发版的粒度对齐：几个平台独立发版，就要有几份说明字段；共用一个顶层字段，串台只是时间问题。
