# 模型给完了，本地再说不行

> 栏目：知识花园 ｜ 合集：Agent 与数字人 ｜ 来源：wiki/concepts/AI调用可靠性与计费观测 ｜ 状态：初稿

**结论先行：** 模型完整返回是一件事，这批结果能不能发布是另一件事。完整返回、业务校验通过、执行归属仍有效、计费已对账，是四个不能互相替代的结论。任何一个没成立，本地都要有勇气说不行，并且把"为什么不行"记成自己的责任，不借模型或网关背锅。

## 四个结论，各说各的

一次 Agent 调用跑完，面前通常摆着四个问题：

1. **模型完整返回**：stop 正常、结束帧齐、用量数据齐备，这是传输层的事实。
2. **业务校验通过**：内容符合业务规则，没有明显跑偏，这是业务层的事实。
3. **执行归属仍有效**：任务的归属（用户、空间、授权租约）在执行过程中没有失效或变更，这是权限层的事实。
4. **计费已对账**：用量已记录、定价来源明确，这是账目的事实。

第一条成立不代表第二条成立，第二条成立不代表第三条成立。每一层都有自己的证据，也都有自己的守卫。把"结果都回来了"当成万能通行证，等于让传输层给权限层和账目层背书，它没这个资格。

## 真实场景：返回完整，但归属没了

来源：知识库 2026-10-11 记录，一个 Agent 项目的离线验证。

场景：一次完整调用跑完，模型给了完整结果，业务校验也过了。但在本地发布前的归属复核发现，任务的执行归属已经变更：授权租约的范围与执行开始时不一致。按规则，禁止发布依然有效，这批结果不能发出去。

这种时候最容易犯两种错，一种比一种常见：

- **看在模型完整的份上放行。** 结果都出来了，守卫再拦岂不是浪费？但归属是安全边界，不是装饰。业务校验只证明内容没问题；归属失效证明的是这批内容已经不归你管。发出去，轻则计费对不上账，重则越权发布。
- **把这次拒绝记成模型或网关失败。** 日志里写"模型调用失败"或者"网关异常"。这是污染观测数据：模型和网关都干得好好的，是本地授权层说不行。

记录里定下的处理规则：

- 保留既有的传输诊断原样：stop、结束帧、用量数据一个不动，它们证明模型确实完整返回了。
- 本地拒绝另记原因（比如归属变更），由统筹层上报，不触发中断补偿流程。
- 本地拒绝就是本地拒绝，不归责模型或网关。

## 谁的锅写谁的名

为什么这条值得单独写一篇？因为"完整返回"太有欺骗性。传输层一片绿灯，人心里就松了；守卫拦下来，看起来像在浪费一次成功的调用。

但归因诚实是观测的第一要求：一次失败被记成谁的责任，决定了以后往哪修。本地授权拒绝被记成网关异常，下次排障就去查网关，真正的归属续期逻辑永远修不到。谁的锅写谁的名，看似道德问题，实际是排障效率问题。

## 本地拒绝怎么写进日志

记日志也有纪律。正确的一次本地拒绝记录，至少包含三部分：

1. **原样保留上游证据**：stop 原因、结束帧、用量数据不做任何改写。后人读日志时，要能一眼看出模型确实干完了自己的事。
2. **独立字段写本地原因**：拒绝归属哪个本地守卫、依据哪条规则、当时看到的归属状态是什么。不跟上游诊断混在同一个字段里。
3. **明确后续动作**：是重试归属续期再发、还是永久丢弃、由谁来决策。日志不写后续动作，就等于把决策推给了下一次排障的人。

这套记法还有一个附带好处：当上游真的出问题时（比如网关超时），日志风格一致，排障的人不需要猜"这个失败到底是谁报的"。
