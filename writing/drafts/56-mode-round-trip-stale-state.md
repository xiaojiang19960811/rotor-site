# 模式切了回来，界面还停在上一站

> 栏目：实验日志 ｜ 合集：Agent ｜ 来源：wiki/projects/数字人 Agent 客户端模式往返切换复盘 ｜ 状态：已写稿·即将发布

结论先说：共享状态要订阅，不要在首次渲染时快照一份私藏。快照在单向流程里够用，一旦用户能来回切换，旧快照立刻变成错乱的来源。模式切换的验收标准，应该是往返用例，而不是单程用例。

## 切回来了，按钮还以为在团队模式

一款桌面 Agent 客户端有两种模式：团队模式和列表模式。底部有一个入口按钮，它的文案和点击行为要跟着当前模式走。

一次改动后出现了这样的现象：用户从团队模式切回列表模式，底部按钮的文案没有变，点击之后的行为也没有变，仍然是团队模式那一套。设置页里还有一份独立的旧状态，同样没有跟上。

根因不在切换逻辑本身，而在读取方式：底部入口只在首次渲染时读取了一次侧栏模式，读到的值被点击闭包捕获，之后就再也不更新了。模式变了，按钮不知道；按钮的文案和行为，都停留在它第一次看到的那个世界里。

## 快照只在单向流程里够用

首次渲染读一次，在很多场景下看起来是合理的：组件挂载时模式是确定的，之后模式不常变，省一次订阅也省一点复杂度。但这个合理性建立在一个隐含前提上：流程是单向的，状态读过一次就不会再变。

往返切换打破了这个前提。用户从团队切到列表，再从列表切回团队，每一次切换都要求界面重新回答"我现在是什么模式"。而快照只能回答"我第一次看到时是什么模式"。两个答案在第一次切换后就分叉了，之后越走越远。

更隐蔽的是第二份状态：设置页自己也存了一份模式。当同一份共享状态在界面上有两个副本，副本之间没有同步机制，漂移只是时间问题。修掉其中一处，另一处迟早还会以别的形式冒出来。

## 修复：让界面订阅模式，而不是各自存一份

修复的方向是把模式收敛到一个共享来源，让所有需要它的界面都订阅这个来源，而不是各自在首次渲染时抄一份：

1. **一个共享模式快照**：团队模式与列表模式的当前值，只存在一个地方。
2. **订阅而不是读取**：底部按钮和设置页都订阅这份快照，模式变化时两者一起更新，不存在"一方更新、另一方不知道"的中间态。
3. **只改前端，不动业务状态**：模式是界面状态，修复它的读取方式，不应该顺带改动会话和账号。改动面越小，越容易确认没有引入新的错乱。

验证也要跟着改：单程用例（团队模式下按钮正确）已经不够了，必须跑往返用例。这次回归覆盖了连续三次团队→列表→团队往返，逐次核对按钮文案、原生新建入口的显隐，并且确认切换过程没有创建额外会话。往返三次都正确，订阅关系才算真的接上了。

## 一条可以带走的检查清单

凡是用户能来回走的状态，都可以按这张清单自查：

1. **这个值是被订阅的，还是被快照的？** 首次渲染读一次、之后靠闭包携带的，都是快照。
2. **它在界面上有几个副本？** 超过一个，就要问副本之间靠什么同步；答不上来，就是漂移的候选。
3. **验收里有没有往返用例？** 只测单程，等于只测了快照还新鲜的那一刻。
4. **切换有没有副作用？** 模式切换本身不应该创建额外会话、不应该改动账号；界面状态的修复，业务状态不应该跟着动。

很多界面错乱看起来是"切换逻辑写错了"，实际上是"读取方式选错了"。切换逻辑可能完全正确，只是它操作的那份状态，界面早就不再看了。

## 一句话收束

共享状态只能有一个来源，界面各处是它的订阅者；凡是用户能来回走的状态，验收都必须跑往返，而不是单程。
