# 「可用」是市场状态，不是通行证

> 栏目：知识花园 ｜ 合集：Agent 与数字人 ｜ 来源：wiki/concepts/AI能力资产治理 ｜ 状态：初稿

**结论先行：** 一个 Skill 或插件在能力市场上标着"可用"，真正的信息量只有一句话：它通过了目录的质量门，当前可以被分发。用户真正想知道的是八个独立问题：质量过关吗？来源读得到吗？我看得见吗？我装得下来吗？我跑得起来吗？能碰业务数据吗？允许外部写入吗？其中任何一个问题的答案，都不能从"可用"两个字推导出来。

## 一个词，八个对象

AI 能力资产包括 Skill、插件、提示词流程、MCP 接入、Automation 和其他可复用的 Agent 工作流。治理它们的重点，不是把所有东西塞进同一个仓库，而是给发现、验证、发布、分发、安装、授权、运行、升级和退役划清边界。实践中至少有八个对象必须分别建模：

1. **实现资产**：独立的仓库、版本、入口脚本和依赖。
2. **目录资产**：稳定 ID、名称、说明、状态、来源和安装方式。
3. **候选草稿**：想法、AI 补全的字段、待维护的内容，不能自动写回正式资产。
4. **分发信息**：Marketplace、企业镜像、制品或 Git 安装入口。
5. **安装副本**：用户环境里的具体版本，不自动随目录状态更新。
6. **运行配置**：MCP、OAuth、环境变量、模型 Provider 和本机私有规则。
7. **权限与授权**：来源读取、资产可见、安装获取、业务数据访问、外部写入。
8. **验证证据**：结构校验、安装、触发、真实任务、权限和外部写入复核。

为什么要拆？因为这八个东西由不同的人、在不同的时间、靠不同的证据产生。最经典的混淆是把目录条目和用户安装副本当成同一个对象：目录里升级了，不代表用户机器上的副本跟着更新了。另一个混淆是让 AI 直接把候选草稿"转正"：AI 可以整理想法、补齐字段、生成评测用例，但把候选提升为"可用"必须是维护者的确认动作。

## 「可用」不等于「你能用」

权限至少要分八层判断：来源读取、资产管理、目录可见、获取安装、本地执行、工具连接、数据访问、外部写入。每一层回答不同的问题，证据各自独立。

三个最容易被骗的结论：

- **「可用」只说资产质量和市场状态。** 它不表示当前用户已经拿到了来源仓库、安装渠道、业务系统或数据的权限。
- **技术会话存在不等于授权。** 已登录的浏览器、可用的 MCP 连接、本机已有的凭据，只证明连接还在，不构成任意读取、修改或发布的授权。发现、发布、安装、配置、访问数据、执行外部写入是六个不同的动作，前一步完成不自动授权后一步。
- **全链路通了，不等于写权限自动开了。** 在一个工时回填的真实场景里，Skill、浏览器登录态和任务候选都就绪之后，创建任务和提交工时仍然是两次独立授权；响应不明时先查询状态，不能直接重试。

## 验证按风险逐层，结论不能互借

能力资产的验证按风险逐层推进：结构与 front matter；单元测试与静态安全检查；隔离环境安装；新线程中的触发与可理解性；使用者权限下的只读真实任务；经独立确认的外部写入，并在写入后反查结果；升级、回滚、卸载能力。

每次验证还要绑定：实现版本、安装副本、运行环境、使用者权限、真实任务、时间和未覆盖边界。这是和[第 9 篇《"已完成"不等于"已验证"》](/writing/09-done-vs-verified)配套的证据观：目录状态、安装成功、一次真实任务成功、持续可用——四个结论不能互相替代。

AI 在这个链条里有明确的边界。它可以识别重复任务并生成候选，从允许读取的来源提取说明和边界，生成候选测试和维护建议，在正式登记的候选集里排序并解释理由。它不可以：把候选自动提升为正式；使用服务账号权限替用户取得运行时业务权限；因为浏览器、MCP 或凭据可用而执行外部写入；把一次安装或演示成功外推为所有用户、环境和版本可用。

退役也是治理的一部分：来源仓库移动或权限撤销、依赖失效、目录说明与实现不一致、安装副本长期未升级——在退役规则确认之前，不自动删除正式资产、用户安装副本或历史证据。

## 小结

能力资产治理的核心动作只有一个：把一个词拆成一组事实。"可用"拆成谁、在哪个版本、什么环境、以什么权限、装了什么、验证了什么。每一句都单独回答，单独验证。从此看到"可用"两个字，先问：对谁可用，在哪儿可用，能用到哪一层？
