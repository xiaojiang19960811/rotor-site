# Git 对象库坏了：别修仓库，从远端重建

> 栏目：日志 ｜ 合集：AI 基础设施 ｜ 来源：wiki/bugs/2026-09-20-Git 对象库损坏与远端恢复 ｜ 状态：初稿

**结论先行：** 一个项目的本地 Git 仓库突然"半死不活"：`git status` 报致命错误读不到 tree，`git fsck` 报大量对象缺失。没有去修复那些坏掉的对象——Git 对象缺失是修不好的，只能补。恢复只用了三步：先确认工作区完好，再从远端拉一个完整克隆，最后把它的对象 pack 直接补进损坏仓库。五分钟后 `git status` 恢复，暂存的修改一个没丢。记住一句话：**Git 的真实源头是远端，不是你本地的 .git；对象丢了不要修，直接从远端拿。**

## 现象：仓库"半死不活"

2026 年 9 月 20 日，数字人 Agent 项目的一个本地工作分支，`git status` 抛 `fatal: unable to read tree`，连当前工作树状态都读不出来。`git fsck --full` 显示索引的 cache-tree 指向了无效对象，并报出大量缺失的 blob、tree、commit。查看 `.git/objects/pack` 是空的——这个仓库基本靠残缺的 loose objects 活着，也就是它大部分时候是"勉强能工作"，直到某次操作触发读到了缺失的那部分。

有意思的是坏得不均匀：当前工作分支的 HEAD 提交在远端同样存在，且 HTTP 远端可正常读取。工作区里还有一批已暂存的修改和未跟踪的新文件——这些是"工作成果"，仓库只是"包装"，恢复过程中绝对不许碰。

## 诊断：先分清"工作区"和"对象库"

Git 仓库里有两个完全不同的东西，损坏时要先分开看。

一是工作区：当前目录的文件，包括已暂存但未提交的修改。这一层在这次故障里是完好的。
二是对象库：`.git/objects` 下的 blob、tree、commit，Git 的"数据库"。这一层是坏的。

诊断的目标只有一件事：确认"远端有没有这批对象"。`git ls-remote` 显示远端可读，且远端分支指向与本地 HEAD 完全相同的提交。这给了恢复方案的合法性：远端有完整的、与本地 HEAD 一致的对象图，本地缺失的对象是可补的，不是不可挽回的。

另一个旧本地分支也缺 4 个对象，但远端没有这个分支，备用远端通道因 SSH 公钥不可用读不到。这个分支的恢复被明确标记为"待确认"，不强行修、不随手删——没法补的对象，就不碰引用它的分支。

## 恢复：补 pack，不修对象

真正的恢复只有三步，没有魔法。

第一步，从远端创建一个临时克隆，不检出工作区。只为了拿到它完整的对象 pack（约 78 MiB）。
第二步，把这个 pack 文件直接复制进损坏仓库的 `.git/objects/pack` 目录。Git 读取对象时会在 pack 里找，loose objects 缺的部分就被补上了。不需要重建索引，不需要改任何引用。
第三步，验证：`git status` 恢复正常且保留全部工作区改动；`git cat-file -p HEAD^{tree}` 可读；`git fsck --full HEAD` 不再报告缺失对象，只剩下正常的历史 dangling 对象。

恢复过程中一条红线被严格执行：没有回退、覆盖或清理工作区里的任何文件。仓库损坏的恢复方案，凡是第一步就让你 `git reset --hard` 或删掉 `.git` 重来的，都是把"包装"修好、把"成果"扔掉的顺序。

## 没有恢复的，是那个旧分支

全仓库的 `git fsck` 仍报告 4 个缺失对象，限定在旧分支。记录写得很诚实：当前分支可继续开发，但全仓库不能宣称无损；坏的旧分支不检出也不删。

这本身就是纪律：恢复范围和验证证据一一对应，能读的分支才算数。旧分支要恢复，必须先从其他备份、开发机或仍持有该分支的远端拿到对象，再谈引用修复。没证据就写"待确认"，不把推测写成结论。

## 收束

这次故障留下四条可复用的纪律：

1. **对象库损坏时，先保护工作区，再补对象。** 工作区是成果，仓库是包装。恢复方案的第一步永远是确认暂存区和未跟踪文件没事。
2. **缺失的 Git 对象不要"修"，直接从远端拿。** 对象缺失没有修复操作，只有补充操作：远端克隆的 pack 补进来，索引不需要动。
3. **恢复范围和验证证据一一对应。** 能读的分支算恢复，没对象补的分支写"待确认"，不碰也不删。全仓库"看起来没事"不是恢复完成的证据。
4. **重要本地分支必须有远端或 bundle 备份。** 只存在于某台机器上的分支，对象一坏就没有任何合法来源能补。dangling 对象不是备份，未推送的分支不是备份。

Git 的设计本身就是分布式的：任何一个完整的远端克隆，都是你本地对象库的合法重建来源。仓库坏了别修仓库，从远端重建。
